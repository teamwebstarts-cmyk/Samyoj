# Taste — Workflow, Communication & Infrastructure
- Expects a research-first, plan-then-build workflow: read the codebase/docs, do web research (incl. competitor and Meta/WhatsApp docs), produce a POC-backed plan, and give a confidence score before executing. The user explicitly instructs to read the project "completely" and "make yourself ready first" before any task work begins. Confidence: 0.93
- Wants every deliverable rechecked end-to-end (bugs, error handling, endpoints, pixel match, responsiveness) and a confidence score before moving to the next screen/task. Confidence: 0.9
- Verifies every code change by running TypeScript typecheck (`npx tsc --noEmit`) on BOTH the client and server packages — treating a clean compile on each as a required gate before considering work done. Confidence: 0.8
- Likes generating subagents/teams to review and critique the work ("critic" reviewers), not just to execute. Confidence: 0.7
- Prefers simplified UX with fewer clicks — removes unnecessary options/steps and prioritizes the most common actions. Confidence: 0.9
- Wants feature/functionality documentation maintained in the project (docs folder, feature/meta docs, list of what was built and what's missing). Confidence: 0.8
- Prefers simple, plain-point explanations: what was done, what was suggested, what's missing, and why — not just raw dump. Explanations must stay very simple: short sentences, plain words (simple English, light Hinglish at most) — the user explicitly asks for simpler wording when a summary is too dense ("simprl akr ark baot") and said heavy Hinglish wasn't understood. The user themself communicates in garbled Hinglish (voice dictation) and expects intent to be inferred and findings summarized in plain points rather than re-asking for clarification. Confidence: 0.97
- Always uses ngrok for public tunnels — never Cloudflare. Confidence: 0.8
- Never exposes credentials/secrets (env variable names, App IDs, secrets) in the UI; secrets stay server-side in .env only. Confidence: 0.95
- Wants an easy one-command local setup (script that configures dependencies/env) so other developers can run the project without friction. Confidence: 0.7
- Likes being told the suggested next task/priority after each phase completes. Confidence: 0.8
- Wants third-party API integrations verified against the vendor's official docs/SDK (e.g., read Sarvam's API reference, use their SDK/MCP) rather than trusting the existing code — docs are the ground truth for param ranges and sample rates. Confidence: 0.85
- Requests broad end-to-end reviews of a whole subsystem (all AI bot + AI calling code), with a written report of what was found before/alongside fixes — not isolated one-off patches. Confidence: 0.9
- For deep-dive assessment tasks, work iteratively "in a loop until you get the best results" — refine the analysis repeatedly until the outcome is optimal, not just a single linear pass. Confidence: 0.85
- Wants multi-specialized agent teams with distinct roles (researcher, code reviewer, critic) for complex tasks — not generic subagents doing the same thing. Confidence: 0.75
- Feature assessment/review deliverables must follow a comprehensive structure: (1) existing state of each feature, (2) what can be improved/enhanced, (3) what new features to add, (4) what is unnecessary and should be removed/deferred, (5) competitor best practices. Confidence: 0.8
- Competitor benchmarking and external platform documentation research are integral, required components of feature assessments — not optional add-ons. The user explicitly wants competitor approaches, Meta API docs, and user/operator perspective research woven into every thorough review. Confidence: 0.8
- Expects exhaustive connection mapping — read every possible connection of a feature across frontend, backend, database, and third-party integrations, not just the surface-level files. Confidence: 0.85
- AI automation scope is strictly channel-limited: the AI voice bot must only be connected to inbound calls — outbound calls are human/agent-only and must never get AI involvement (corrected emphatically when a summary implied otherwise, and re-confirmed explicitly in follow-up). Confidence: 0.95
- After a plan is approved, the assistant should execute all remaining phases without asking "what next?" — "do itnow" means everything, not a menu selection. Don't keep polling for direction mid-execution. Confidence: 0.7
- At planning time, wants ONE consolidated recommended approach presented (with a proper, complete POC plan + confidence score) rather than multiple approaches to compare/evaluate — "ek abr...proper poc ki saat baat." Converge on a single path and proceed. Confidence: 0.8
- When replacing a feature or component with a new version, remove the old one — clean replacement, not accumulation. The user explicitly rejects keeping both: "ab new wlai hai tho ye purar wlai hata tdo" (now there's a new one, remove the old one). Confidence: 0.85
- The assistant is expected to proactively identify opportunities to improve or refine the work beyond the literal specification — "batterkarko ho toh dkeh lean" (if it can be made better, look into it). Don't just implement specs verbatim; use judgment to enhance. Confidence: 0.8
- When a problem is clearly identified (e.g. "voice latency is too slow"), prefers targeted, minimal-scope fixes over broad vendor API surveys or exhaustive capability documentation — research should serve the fix, not become a deliverable in itself. Confidence: 0.75
- AI voice agents must follow natural, graceful conversational flows for handoffs: check agent availability BEFORE promising a connection, offer alternatives (callback scheduling, WhatsApp follow-up) when unavailable, maintain conversational continuity with "let me check" / "here's what I can do" framing, and always end calls with a clear resolution — never abrupt disconnection or dead silence. Confidence: 0.8
- One brain powers both text chat and voice channels — the same AiBot entity handles WhatsApp text messages and WhatsApp voice calls, with voice-specific rules (short replies, no markdown, language matching) injected at the channel level by the server. Architecture must preserve this unified brain approach, not split chat and voice into separate systems. Confidence: 0.9
- Voice AI agents in multilingual markets (e.g., India) must auto-detect the caller's spoken language from STT transcripts and automatically switch TTS synthesis to reply in that same language — the system adapts to the caller, not the other way around. A hardcoded default language per deployment is insufficient; the STT→TTS pipeline must carry detected language codes end-to-end. Confidence: 0.85
- When a user initiates a call from a chat/inbox conversation, they should be seamlessly redirected to the dedicated Calls page where the live call controls and transcript/captions appear side by side — the calling experience should be centralized, not fragmented across different pages. Confidence: 0.7
- API clients that call multiple model variants of the same vendor (e.g., `sarvam-105b` vs `sarvam-105b-conversations`) must dispatch parameters conditionally per variant — unsupported parameters can cause silent/empty responses rather than explicit errors, and the breakage is indistinguishable from a model failure. When adding a new model variant, audit every parameter sent to ensure compatibility. Confidence: 0.85
- When debugging AI pipeline failures (empty responses, fallback loops, silent errors), first isolate by testing the raw third-party API call directly (curl) — this separates API-level issues from application-code issues before any code changes are made. Confidence: 0.8
- Before handing off for the user's manual testing, the assistant should run its own comprehensive technical self-tests — direct API isolation calls, full E2E pipeline simulations, and edge cases — so it discovers issues before the user does. Results should be presented as a structured summary (table format preferred) covering each test case, latency figures, and pass/fail status. Confidence: 0.85
- When presenting a large catalog of configurable options (especially sensory ones like TTS voices, where the user must audition each choice), curates down to a small, high-quality selection of the most recommended/popular items rather than exposing the full vendor inventory. The user explicitly rejects exhaustive lists: "only add top 10, do research and choose the best." Default to curation over exhaustiveness. Confidence: 0.75
- Wants feature assessments and reviews organized by the actual UI sidebar/navigation structure of the dashboard — not by backend module organization or server routers. When evaluating completeness, map findings to the visible left-sidebar options the user interacts with. Confidence: 0.9
- Wants comprehensive documentation deliverables to include a scored self-assessment section that (a) rates the documentation/analysis quality itself with a numerical score (not just feature or code scores), (b) reviews from multiple perspectives (code reviewer, architect, UX designer, product manager, security auditor, Meta developer), (c) explicitly lists every gap, error, or missing connection found during the recheck, and (d) provides actionable "how to achieve" implementation guidance (with specific code locations, file paths, and phase assignments) for each identified gap — the user explicitly asks "how we achieve them" rather than just problem identification. Confidence: 0.85
