# Taste — UI & Design

- Prefers pixel-perfect implementation of provided design mockups: read reference images pixel-by-pixel and match exact spacing, sizes, alignment, and content — not approximate. Confidence: 0.95
- Provides exact text-based UI specifications inline (card titles, descriptions, button labels, flow directions like "lands on Personality") and expects them to be implemented exactly as stated — textual specs carry the same weight as visual mockups. Confidence: 0.85
- Uses WhatsApp's chat UI as the canonical reference for inbox/chat design (bubble colors #D9FDD3 sent / #FFFFFF received, #EFEAE2 chat bg, Roboto/SF Pro fonts, ~8px bubble radius, read-receipt ticks, 24h reply-window badge). Confidence: 0.9
- Wants a glassmorphism aesthetic: translucent panels, backdrop-blur, frosted-glass cards with soft shadows and gradient tints. Confidence: 0.85
- Treats icons as high priority: wants custom SVG icons that match the design exactly (not library defaults), plus small hover tooltips on every icon explaining what it does. Confidence: 0.9
- Demands full responsiveness across mobile/tablet/desktop with no overlapping text, no blank gaps, and app screens that fit the viewport without page-level scroll. Confidence: 0.9
- Prefers square-cornered (rounded-rect) selection/status indicators over circular ones. Confidence: 0.75
- No mock data — analytics, graphs, and stats must be wired to real backend data with correct logic/mathematics. Confidence: 0.95
- Avoids multiple/vertical scrollbars in composer panels; prefers side-by-side layouts (form on left, live preview on right) that don't require scrolling. Confidence: 0.8
- Chat-scoped notifications only (inline notices like WhatsApp, e.g. "AI bot paused") — no global page-level toasts for success; success is shown by the message bubble itself. Confidence: 0.85
- Wants skeleton loaders for async-loaded content (conversation lists, chat threads) and smooth transitions when content appears. Confidence: 0.7
- When presenting many configurable options (especially sensory ones like TTS voices), requires inline preview/demo controls so users can audition each choice before selecting — listing names/labels alone is insufficient; the user must be able to experience the difference to make an informed decision. Confidence: 0.85
- Real-time event notifications (e.g., incoming calls) should be non-blocking, banner-style overlays at the bottom/side of the screen — like a mobile OS incoming-call banner — not full-screen modals with backdrop. The user must be able to keep interacting with the rest of the application while the notification is visible. Confidence: 0.8
- Voice/SarvAM configuration should be embedded as a tab within the bot editing flow (e.g., an "AI call" tab in AiBotPage), not in a separate standalone Settings page. Users configure voice sound alongside personality and training in the same slide-over. Confidence: 0.9
- Friendly labels, no provider jargon — use human-readable names ("AI call" tab, "Shubh" voice) instead of technical identifiers ("TTS/STT Configuration", "bulbul-v3-male-hi"). Confidence: 0.85
- Knowledge base / training data (FAQs, URL imports, PDFs) added to a brain must be fully visible in the training configuration UI — not hidden, collapsed, or obscured. The user emphasizes transparency: "show the data completely, we don't have to hide anything." Confidence: 0.8
- Training data items must support full CRUD from the training configuration UI: users can add, configure, edit (change), and delete knowledge base data directly where they are editing the brain. Confidence: 0.8
- Analytics/metrics must display rounded whole numbers — no decimal places and no redundant percentage clutter on values (e.g., "93.7%" should read "94" or just the bare rounded number). Confidence: 0.9
- All screens must share one consistent design system (the Samyoj UI skill doc: green primary on white/soft green-tinted surfaces, thin borders, soft shadows, rounded cards, restrained status pills). Redesigns should reuse the exact components, sizes, and layout patterns from Inbox/Calls/Dashboard rather than inventing per-feature themes — the user repeatedly asks for "exactly the same width and height as the inbox card" and to match the same UI patterns across Calls, Campaigns, Templates, Orders, and Tickets. Confidence: 0.95
- Avoid generic admin/telecom/enterprise-dashboard aesthetics and purple-heavy themes. The product should feel like "one calm workspace for WhatsApp operations" — minimal decorative noise, no heavy gradients, "show less, but make every visible thing useful." Confidence: 0.9
- Actively trims unnecessary features and decorative elements from the UI (snooze, payment links, connection settings, campaign summary cards, decorative hero art, redundant labels like "LIVE · ANSWERING") — keep only what is needed for the user's task. Confidence: 0.9
- Card/button widths should size to their content rather than being hardcoded fixed widths; layout grids should reflow responsively instead of forcing horizontal scrolling. Confidence: 0.8
- Chart hover behavior: hovering a donut/graph segment shows a small tooltip with only that segment's details, while the center/default value stays unchanged (don't swap the middle number on hover). Confidence: 0.8
- Message-level dropdown menus should open on an explicit click of a visible affordance (chevron/drop-down), not on hover or right-click; conversation-list context menus do open on right-click. Confidence: 0.75
- Exposes user-customizable UI settings: page gutter (left/right inset around cards), text size scale (Small/Default/Large via a single html font-size scale), display density, and a curated set of professional font families to choose from. Confidence: 0.85
- Toast notifications must be compact (small height), few in number, and free of progress bars — tall/stacked toasts with progress indicators are rejected as "unnecessary feeling out." Confidence: 0.8
- Filter/toolbar rows (tabs, status chips, segmented controls) should collapse to a single line on desktop with reduced padding/margins — horizontal scroll is acceptable on mobile, but never multi-row wrapping on desktop. Confidence: 0.8
- Wants AI-assisted generation embedded in configuration flows: a "Write personality" button that drafts a bot personality/system prompt from a plain-language user note, AI-suggested FAQ/training Q&As from business info, and personalized help questions suggested from the current chat context — users type simple ideas, the AI produces the structured content. Confidence: 0.8
- Create/save actions in multi-step configuration flows (setup → train → try) must appear only on the final step — nothing is auto-created on intermediate saves, and test/try must work with unsaved in-progress configuration before the explicit Create click. Confidence: 0.85
- On mobile, auth/login pages show only the form card, full-width and not shrunken, with decorative showcase panels and promo CTA cards removed; the desktop version should be left essentially untouched. Confidence: 0.75
- In-app help should be an AI assistant with curated common questions (plus AI-suggested personalized questions), not a ticket system — tickets are seen as unnecessary for the user. Confidence: 0.7
