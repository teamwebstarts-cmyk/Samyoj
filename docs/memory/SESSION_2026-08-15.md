## 2. WhatsApp number data isolation

One shared Postgres. Each connected number is a durable workspace via `whatsappNumberId`.

| Rule | Current truth |
|------|----------------|
| Same displayed phone reconnects | Same workspace even if Meta `phoneNumberId` changes (`saveWhatsappConnection` matches `normalizedPhoneNumber`, then provider id) |
| Different numbers | Separate contacts, tags, consent, inbox, campaigns, tickets |
| Disconnect | Soft `isActive=false`. Do **not** delete number rows or history |
| Client selection | localStorage stores Meta `phoneNumberId` (`WhatsAppNumberContext`) |
| API header | Current DB id `X-WhatsApp-Number-Id` (`active-number.ts`) |
| Multiple active numbers | Missing header → **409**. Never pick “latest” |
| Contacts | `@@unique([organizationId, whatsappNumberId, normalizedPhone])` |
| Campaigns | Require number ownership. Send fail-closed: `optedIn` + `consentSource` + `consentAt` + no `optOutAt` (`hasAuditableCampaignConsent`) |

WhatsAppNumber also `@@unique([phoneNumberId])` and `@@unique([organizationId, normalizedPhoneNumber])`.

**Migrations:** historical `20260808120000_unique_whatsapp_phone_number_id` **DELETEs** duplicate `WhatsappNumber` rows. Never raw `prisma migrate deploy` for fresh installs. Use fail-closed `db:migrate-startup-safe` / reconciliation allowlist + backup.
